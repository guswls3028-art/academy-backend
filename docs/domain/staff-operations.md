# 직원·근태·정산 도메인

학원 대표와 권한을 위임받은 강사·조교가 직원을 등록하고 근태·직원 선결제 환급·월마감을 관리하는 현재 운영 정책이다. 이 기능은 근태와 월별 내부 정산을 보조하며, 세무·노무 급여 엔진이나 법정 임금명세서를 대신하지 않는다.

## 권한

| 행위 | 대표·admin | `is_manager=true` 강사·조교 | 일반 강사·조교 |
|------|------------|-----------------------------|----------------|
| 직원·시급·비용·정산 조회/관리 | 가능 | 가능 | 불가 |
| 본인 출퇴근·휴게 | 가능 | 가능 | 가능 |
| 대표 비밀번호 초기화 | 불가 | 불가 | 불가 |
| admin 비밀번호 초기화 | 대표만 가능 | 불가 | 불가 |
| 급여 조정액 입력 | 가능 | 가능 | 불가 |

- 권한의 정본은 현재 테넌트의 활성 `TenantMembership`이다. `User.tenant` 포인터만으로 권한을 부여하지 않는다.
- 화면에 표시하는 직위(`DIRECTOR` 실장, `INSTRUCTOR` 강사, `ASSISTANT` 조교,
  `STAFF` 직원)는 소개용 정보이며 로그인 계정 역할이나 권한을 부여하지 않는다.
  대표 직위는 대표 멤버십에서 파생한다.
- 계정 유형은 활성 `TenantMembership.role`에서 `OWNER`, `ADMIN`, `TEACHER`,
  `STAFF`, `NONE`으로 응답한다. 이전 클라이언트 호환용 `role` 필드는 강사
  명부 동기화 계약을 유지하지만 직위로 표시하지 않는다.
- `is_manager`는 강사·직원 계정에 위임한 값이고, `can_manage_staff`는 대표·admin의
  고정 권한까지 합친 유효 권한이다. 대표·admin은 직원 화면에서 이 값을 끄거나
  퇴사·영구삭제할 수 없다. 비활성 멤버십·퇴사 직원·계정 없는 행은 과거
  `is_manager` 값이 남아 있어도 유효 권한을 반환하지 않는다.
- 일반 직원의 출근은 본인에게 배정된 활성 `StaffWorkType`만 허용한다.
- 배정 근무유형이 여러 개면 출근 전에 유형과 단가를 직접 선택한다.
- 인증 로그인 자체는 `WorkRecord`를 만들지 않는다. 조교가 로그인 선택 화면이나
  상단 근무 상태에서 근무유형을 선택해
  `POST /staffs/{staff_id}/work-records/start-work/`를 성공시킨 시점부터만
  근무시간을 계산한다. `출근하지 않고 로그인`은 근무 API를 호출하지 않는다.
- 직원 명부 읽기는 활성 테넌트 직원에게 허용할 수 있지만, 강사 명부 쓰기는 급여관리 권한이 있어야 한다.
- 관리자 권한과 비밀번호 초기화는 운영 감사 로그를 남긴다.
- 시급 태그와 직원별 시급 배정의 생성·수정·삭제는 변경과 감사 이력을 같은
  트랜잭션에 저장한다. 이력 저장 실패 시 503과 재시도 안내를 반환하고 기존
  시급·배정·삭제 대상은 보존한다. 복구 후 다시 실행하면 변경과 이력이 한 번씩
  저장된다. 근무 시작 당시 고정된 시급과 과거 급여 스냅샷은 재계산하지 않는다.
- 비밀번호 초기화는 직원 행과 연결 사용자 행을 한 트랜잭션에서 각각 잠근다.
  nullable 사용자 JOIN 전체를 잠그지 않으므로 PostgreSQL에서도 계정 없는 직원은
  검증 오류로 닫히고, 연결 계정이 있으면 동일 테넌트 권한 판정 뒤 한 번만 변경된다.
- 직원 계정의 생성·비밀번호 재설정은 입력한 비밀번호를 즉시 정상 비밀번호로
  저장하고 기존 토큰만 폐기한다. 직원에게 첫 로그인 변경을 강제하거나 권장하는
  `must_change_password` 상태를 만들지 않으며, 과거 상태가 남아 있으면 재설정 시
  해제한다. 본인이 원할 때 프로필의 공통 비밀번호 변경 경로를 사용할 수 있다.

## 직원 생명주기

1. 등록 시 직위는 실장·강사·조교·직원 중 하나, 계정 유형은 강사 또는 일반
   직원 중 하나로 별도 선택한다. 계정을 만들면 초기 비밀번호는 4자 이상이며
   즉시 로그인에 계속 사용할 수 있다.
2. 재직 중 이름·전화·직위 변경은 직원 정보만 갱신한다. 계정 유형 변경은 Staff,
   연결 User, TenantMembership, 강사 명부를 한 트랜잭션에서 맞춘다.
3. 퇴사 처리는 `is_active=false`로 전환한다. 진행 중 근무가 있으면 거부하며, 로그인 멤버십과 관리자 권한을 중지한다.
4. 근무·비용·월마감·급여 스냅샷은 퇴사 후에도 보존한다.
5. 영구 삭제는 오등록 정리용이다. 위 이력이 한 건이라도 있으면 거부한다.
6. 재입사는 역할을 명시해 재활성화한다.

## 근태 불변 규칙

- 신규 실시간 퇴근은 학원 시간대의 `end_date`와 `end_time`을 함께 저장한다.
  24시간 이상 및 월 경계를 넘긴 근무도 실제 경과 분으로 계산하며 정산 귀속 월은
  출근 `date`를 따른다. 관리자도 종료 날짜를 정정할 수 있고 감사 이력에 남긴다.
  종료 날짜가 없는 기존 기록은 종전 익일 추론을 유지하고 과거 금액을 일괄 재계산하지 않는다.
- 실제 종료 일시가 출근 이전/동일하거나 유급시간 999.99시간·금액 2,147,483,647원을
  초과하면 저장하지 않는다. 실시간 퇴근 실패는 열린 기록과 휴게 상태를 보존하며
  관리자가 실제 출퇴근 일시를 정정한 뒤 정상 종료할 수 있다.
- 수정 폼이 동일한 계산 입력을 다시 보내도 수동 확정 금액·시간을 유지한다.
  잠긴 원본 행과 비교해 실제 입력이 달라졌을 때만 자동 재계산한다.

- 직원별 미종료 근무는 최대 한 건이다.
- 시작과 종료 시각은 같을 수 없다. 종료가 시작보다 이르면 다음 날 종료로 계산한다.
- 휴게·식사시간 합계는 전체 근무시간보다 짧아야 한다.
- 휴게 중 generic PATCH로 근무를 종료할 수 없다. 표준 퇴근 액션이 휴게를 정산하고 종료한다.
- 일반 직원은 퇴근 요청으로 `adjustment_amount`를 입력할 수 없다.
- 월마감 이후 해당 직원·월의 근무와 비용은 생성·수정·삭제할 수 없다.
- 적용 시급은 출근 시점에 `resolved_hourly_wage`로 고정한다. 이후 단가 변경이나 재계산이 이미 시작된 근무에 소급 적용되지 않는다.
- 종료된 기존 기록은 메모 등 비급여 필드를 저장해도 금액을 다시 계산하지 않는다.
  신규 종료 기록, 퇴근 처리, 급여 계산 입력 변경, 관리자의 명시적 `자동 계산으로
  복원`에서만 현재 산식을 적용한다.
- 직원별 `hourly_wage=0`은 무급 또는 별도 정산을 뜻하는 유효한 명시값이다.
  값이 `NULL`일 때만 근무유형 기본 시급으로 대체하며, 0을 truthy fallback으로
  덮어쓰지 않는다.
- 현재 근무 응답은 선택한 `work_type`, `work_type_name`, 출근 시점
  `hourly_wage`를 함께 반환한다. PC·모바일은 이 값을 표시하며 이름이나 현재
  배정값으로 진행 중 기록의 유형·시급을 다시 추론하지 않는다.

## 근무 생명주기 구조

- 인증 토큰과 로그인 시각은 근무 상태가 아니다. 유급 근무의 유일한 상태는
  테넌트·직원별 열린 `staffs.WorkRecord(end_time IS NULL)`이다.
- `apps.domains.staffs.selectors`가 현재 근무와 기간 기록을 테넌트 범위로 읽고
  현재 상태 응답을 만든다. 다른 테넌트의 `Staff`가 들어오면 빈 값으로
  대체하지 않고 권한 오류로 닫힌다.
- `apps.domains.staffs.services.work_records`가 출근, 휴게 시작·종료, 퇴근과
  최종 근무시간·금액 계산을 소유한다. 각 상태 전이는 행 잠금과 월마감 검사를
  같은 트랜잭션 안에서 수행한다.
- HTTP view는 대상 직원·기록에 대한 본인/급여관리 권한과 요청 형식만 확인한
  뒤 selector/service에 위임한다. view에서 `end_time`, 휴게 누계, 시급 또는
  금액을 별도로 계산하지 않는다.
- 관리자 수기 CRUD는 기존 `WorkRecordViewSet`에 남지만 실시간 출퇴근 액션과
  같은 `WorkRecord`·월마감·단가 고정 규칙을 사용한다. 별도 조교 타이머 테이블이나
  로그인 기반 비용 기록은 만들지 않는다.
- 급여 관리자가 수기로 근무기록을 만들거나 수정·삭제하면 같은 트랜잭션에서
  `staff.work_record_created`, `staff.work_record_updated` 또는
  `staff.work_record_deleted` 감사 로그를 반드시 남긴다. 감사 저장이 실패하면 원
  근무기록 변경도 롤백한다. 수정 로그는 변경 필드와 함께 날짜·직원 ID의 정확한
  before/after 값을 항상 남겨 날짜나 직원을 옮긴 이력을 재구성할 수 있게 한다.
  관리자 `POST /staffs/work-records/{id}/recalculate/`의 자동 계산 복원도 같은
  `staff.work_record_updated` 감사로 금액·시간·수동 수정 플래그의 전후 값을 남긴다.
  감사 실패 시 복원도 롤백하며 월마감·직원 및 테넌트 권한 경계는 유지한다.
  로그에는 actor와 tenant,
  record/staff/work-type ID, 날짜·시간·계산 입력·금액, `source=payroll_manager_manual`,
  생성 당시 로컬 날짜를 기록하고 이름·전화·메모는 기록하지 않는다. 삭제 로그는
  행 삭제 뒤에도 급여 사실을 재구성할 수 있는 before snapshot이다. 본인 실시간
  출퇴근은 서버 로컬 날짜를 쓰는 별도 경로이므로 이 수기 source로 표시하지 않는다.

## 조교 본인 흐름과 기간 기록

1. 새 자격증명 로그인이 성공하면 프론트는 `tenantRole=staff` 조교에게만
   근무 시작 선택을 한 번 요청한다.
2. 조교는 배정된 클리닉·현장 등 근무유형을 골라 즉시 출근하거나,
   `출근하지 않고 로그인`으로 매뉴얼 확인 등 비근무 이용을 계속한다.
3. 출근 후 PC 헤더와 모바일 상단 근무 상태에서 경과시간, 선택 유형, 적용
   시급을 확인하고 휴식·복귀·퇴근한다.
4. 퇴근하면 서버 시각으로 기록을 닫고 휴게·식사시간을 차감한 뒤
   `work_hours`, `amount`를 계산한다.
5. 본인은 `GET /staffs/{staff_id}/work-records/?date_from=&date_to=`와
   `GET /staffs/{staff_id}/summary/?date_from=&date_to=`로 자기 기록과 기간
   합계를 읽는다. 급여 관리자는 동일 API로 대상 직원을 조회할 수 있다.

일반 직원은 다른 직원 ID로 기간 기록이나 합계를 조회할 수 없다. 테넌트와
연결 사용자 검증을 모두 통과해야 하며 실패는 `403`으로 닫힌다. 개인 화면의
근무기록은 읽기 전용이다. 정정·삭제·월마감은 급여 관리 화면의 기존 권한과
감사 절차를 따른다.

과거 `/core/profile/attendance/`의 수기 `core.Attendance`는 근무유형 배정과
출근 시점 단가를 복원할 수 없는 별도 레거시 데이터다. 기존 행과 API는 삭제하지
않지만, 현재 PC·모바일 본인 근무 화면과 정산 계산은 이를 섞지 않고 정본
`staffs.WorkRecord`만 사용한다. 운영상 필요한 과거 수기 행은 원본을 보존한 채
별도 확인하며 자동 이관·재계산하지 않는다.

## 직원 선결제 환급과 월마감

- 이 항목은 직원이 개인 비용으로 먼저 결제한 환급 대상만 등록한다. 학원 법인카드·계좌로 직접 지출한 비용은 넣지 않는다.
- 새 환급은 요청 값과 관계없이 `PENDING`으로 생성한다.
- 환급 금액은 1원 이상이어야 한다. 0원·음수 값은 생성과 수정 모두 거부하며 기존 행을 바꾸지 않는다.
- 대기 중인 환급은 날짜·항목·금액·메모를 정정하거나 삭제할 수 있다.
- 승인·반려는 관리자만 수행할 수 있는 상태 전이이다.
- 승인·반려와 `staff.expense_reviewed` 감사 저장은 같은 트랜잭션이다. 감사 저장이
  실패하면 503을 반환하고 대기 상태·승인자·승인 시각을 보존한다. 같은 항목에서
  재시도하면 정상 처리와 감사가 함께 한 번만 저장된다.
- 승인·반려된 환급은 감사 이력 보존을 위해 수정·삭제할 수 없다. 정정은 새 대기 항목으로 등록한다.
- 월마감은 append-only이며 근태·환급 정산 스냅샷을 함께 생성한다.
- `MONTHLY` 직원은 자동 월마감을 거부한다. 근로계약·수당·공제를 확인해 별도로 정산한다.
- 마감 상태 조회가 실패하거나 진행 중이면 클라이언트는 쓰기를 허용하지 않는다.
- 정산 엑셀은 해당 월에 근무·환급 기록이 있는 직원 전원의 스냅샷이 있어야 생성한다. 현재 재직 여부를 과거 월에 소급하지 않는다.
- 스냅샷 ID 집합과 revision을 워커 payload에 고정하며, 워커는 정확히 같은 집합만 조회한다.

## 금액 표시 계약

현재 자동 계산:

```text
유급 분 = 출퇴근 실제 분 - 휴게 분 - 식사 분
근무기록 금액 = 유급 분 × 적용 시급 ÷ 60 + 관리자 조정액 (1원 HALF_UP)
정산 합계(공제 전) = 근무기록 금액 + 승인 선결제 환급
```

- `work_hours`의 0.01시간 반올림은 표시용이다. 금액 계산에 이 값을 다시 곱하지
  않고 원본 유급 분을 사용해 232분 × 15,000원 ÷ 60 = 58,000원을 보존한다.
- 관리자 근무 수정은 현재 행을 잠근 뒤 출퇴근·휴게·식사·금액 범위를 검증한다.
  먼저 처리된 시간 정정 뒤에 들어온 부분 수정도 최신 시간에 맞아야 하며,
  맞지 않으면 400과 사유를 반환하고 확정된 시간·금액·감사를 변경하지 않는다.
  유효한 부분 수정은 최신 기록에 합쳐 저장한다. 회귀:
  `staffs.tests.test_payroll_update_integrity`의 급여 보존·정상 수정·환급 재시도.
- 시급제 직원은 기본 공제율 3.3%를 적용한다. 화면·PDF·엑셀은 공제 전 급여,
  기본 공제 3.3%, 공제 후 급여, 승인 환급, 이체 예정액을 구분한다.
- 직원별 월 급여에 3.3%를 적용해 1원 `ROUND_HALF_UP`한다. 3% 항목도 같은 방식으로
  반올림하고 0.3% 항목은 총공제와의 차이로 맞춘다. 전체 합계는 직원별 계산값을
  합산하며, 합계에 공제율을 다시 적용하지 않는다. 승인 환급비는 공제 대상이 아니다.
- 마감 후에는 불변 스냅샷의 급여·환급에서 같은 정책으로 산출한다. 기존 원금·이력은
  재작성하지 않으며 API의 `reference_*` 이름은 호환성을 위해 유지한다. 마감 조회의 추가 읽기 전용
  `default_deduction`은 공제 구성·합계, 공제 후 급여, 이체 예정액을 반환한다.
- PDF 제목은 `급여·환급 정산서`다. 엑셀도 같은 서버 정책을 사용하고 이름·계정을
  수식이 아닌 문자열로 저장한다. `staff_export:deduction-v2` 멱등키가 구형 공제 전
  전용 파일의 재사용을 막으며 스냅샷 ID/revision 검증과 Tools 워커 경계는 유지한다. 새 payload의
  `format_version=2`와 버전 포함 revision은 순차 교체 중 구형 워커가 구형 파일을 새
  캐시에 저장하지 못하게 한다. 신형 워커는 기존 대기 작업도 계속 처리한다.
- 이체 예정액은 공제 후 급여 + 승인 환급이며 송금 완료 상태가 아니다. 법정 임금명세서,
  근로소득세·4대보험·기타 공제 자동 계산 및 실제 송금 추적은 제공하지 않는다.
- 연장·야간·휴일수당을 자동 계산하지 않는다. 적용 요건과 계산은 별도 확인한다.
- `MONTHLY`에는 기본급·일할·연장·휴일·공제 정책이 아직 없다. 신규 선택과 자동 월마감을 막고, 기존 값은 `월급(수동 확인)`으로 표시한다.

## 목록·내보내기 계약

- 직원 도메인 목록은 `page_size`를 지원하며 최대 500건으로 제한한다.
- 직원 명부·근무유형/배정·근무·환급·월마감·급여 스냅샷과 본인 근무기록은
  tenant·역할·필터와 허용된 정렬을 적용한 뒤, `StaffDomainPagination`에서
  주 정렬과 같은 방향의 ID 보조키를 붙이고 페이지를 자른다. 같은 이름·날짜·시각·월의
  행도 다시 조회하거나 다음 페이지로 이동할 때 같은 순서를 유지한다.
- 관리 화면과 직원 본인 화면은 `page_size=500`을 한 페이지 크기로 사용하며
  전체 페이지의 완전성을 확인한다. 중간 조회 실패·중복·누락과 재조회 및 엑셀 계약은
  [프런트 직원 운영 문서](../../../frontend/docs/STAFF-CLOCK-IN.md)가 소유한다.
  이 조회 변경은 원본 근태·환급·불변 스냅샷의 금액이나 마감 상태를 재작성하지 않는다.
- 급여 스냅샷 조회는 `staff`, `year`, `month` 서버 필터를 적용한다.
- 신규 스냅샷은 월마감 당시 직원명을 복제해 이후 개명·오타 수정이 과거 정산서를 바꾸지 않게 한다. additive migration 이전 행은 현재 이름으로 안전하게 fallback한다.
- PDF는 한글 폰트를 등록해 이름과 한글 항목명이 깨지지 않게 한다.

## 월 급여 전체 현황

- 저장된 급여 스냅샷이 있으면 시간·공제 전 급여·승인 환급·합계는 스냅샷을 사용한다.
  현재 원장 합계와 다르거나 미완료 기록이 남으면 `RECONCILIATION_REQUIRED`로 표시하며
  과거 스냅샷이나 근무 자료를 자동 수정하지 않는다. 근무유형별 내역은 현재 원장 자료다.
  마감 잠금만 남은 퇴사 직원도 누락하지 않는다. 정상 마감 인원은 대사 필요 인원을 제외한다.
- 시급 태그 중복 배정은 직원 행 잠금 안에서 검증해 400과 사유를 반환한다.
  기존 직원별 시급은 덮어쓰지 않으며 다른 테넌트 배정은 기존 권한 경계에서 거부한다.
  브라우저의 일괄 선택·부분 실패 복구 계약은 [프런트 직원 운영 문서](../../../frontend/docs/STAFF-CLOCK-IN.md)를 따른다.

- `GET /staffs/payroll-overview/?year=&month=`는 현재 테넌트의 재직 직원과 해당
  월 근무·환급·마감 이력이 있는 퇴사 직원만 반환한다. 다른 테넌트 행은 합계와
  목록 모두에서 제외한다.
- 한 번의 월별 읽기에서 근무시간, 근무기록 금액, 근무유형별 시간·금액,
  승인·대기 환급, 공제 전 합계, 3.3% 비교 참고 워터폴, 근무유형 배정,
  진행 중·계산 미완료 기록, 마감·스냅샷 상태를 직원별로 묶는다.
- 동일 직원·날짜·출퇴근·근무유형이 같은 기록, 12시간 이상 근무, 미퇴근,
  계산 미완료, 관리자 수동 수정은 지급 전 확인 신호로 반환한다. 이 신호는
  기록을 숨기거나 수정·정산을 차단하는 권한 가드가 아니다.
- `NEEDS_REVIEW`는 진행 중 근무, 계산 미완료, 대기 환급, 재직 직원의 시급태그
  미배정 또는 월급 수동 확인이 남은 미마감 월이다. 마감과 스냅샷 중 한쪽만
  존재하면 `RECONCILIATION_REQUIRED`로 닫는다.
- 완전한 마감·스냅샷 쌍은 append-only 과거 정본이므로 현재 근무유형 배정이
  바뀌어도 `CLOSED`를 다시 검토 상태로 소급하지 않는다.
- 현황 합계와 본인 summary는 같은 서버 정책으로 참고 공제와 환급 포함 최종 이체
  참고액을 반환한다. 실제 공제 적용 여부와 지급액은 외부 세무 절차에서 확정한다.

## 개인정보 최소화

직원 관리에는 이름, 연락처, 직위, 계정 역할, 재직 상태, 업무별 단가와 정산
이력만 저장한다. 주민등록번호 같은 고위험 정보는 별도의 법적 근거·암호화·접근통제·파기 정책 없이 추가하지 않는다.

프론트 화면·실패·반응형 계약은
`frontend/docs/STAFF-CLOCK-IN.md`가 소유한다.
