# V1.11.0 Release Notes

**Status:** Production-deployed / GO

**Release date:** 2026-07-26 KST

**Scope:** Privacy-safe user-incident capture, five-minute operator alerting to
the fixed controlled number, and an independent CloudWatch fallback for API
failure modes that cannot write to the database

## 1. Decision

GO. Authenticated users can submit explicit problem reports, persistent
frontend failures are reported automatically, and user-facing backend 5xx
responses produce bounded incident signals. New signals are grouped and sent
as a short SMS to `01031217466`; message content contains counts and a `/dev`
prompt only.

This release adds CloudWatch metric/composite alarms, GitHub Actions IAM, and a
five-minute production cron, so the infrastructure segment advances from
V1.10.0 to V1.11.0. No application migration is required.

## 2. Delivered Behavior

- `POST /api/v1/core/problem-reports/` is authenticated and tenant-bound.
  It accepts manual reports and generic frontend error metadata, strips query
  strings, generalizes numeric/UUID route parameters, and stores no raw user
  identity or exception body in the SMS.
- Browser `error`, `unhandledrejection`, and persistent React error-boundary
  failures use the shared authenticated API client. Automatic reports require
  recurrence, use a 15-minute session dedup window, and do not replace chunk
  reload recovery.
- User-facing backend 5xx responses emit a PII-free application log
  immediately and enqueue a sampled `OpsAuditLog` write without delaying the
  response.
- Distributed tenant/user/source throttling allows at most 12 problem reports
  per hour. Manual and automatic sources have separate buckets.
- `check_dev_alerts` scans a durable two-day window with a 30-minute overlap,
  groups repeated incidents into 15-minute fingerprints, and records success
  only after Solapi reports `sent_success`.
- The scheduled workflow evaluates user incidents every five minutes and the
  existing full alert set hourly. It runs only the immutable API digest from
  the latest complete successful release manifest.
- `academy-api-Target5XX` and `academy-api-UnHealthyHosts` feed the
  `academy-api-UserImpact` composite alarm. Alarm transitions have an
  SSM-backed dedup token and can send a fixed, database-independent signal.
- The SMS recipient is exact-allowlisted in code and environment. The setup
  script also normalizes `SOLAPI_SENDER` to the production account's sole
  ACTIVE registered sender, the same controlled number.

## 3. Privacy, Isolation, and Failure Policy

- SMS text is limited to 90 UTF-8 bytes and contains incident-type counts only.
  Student names, phone numbers, user input, URLs with query strings, exception
  messages, and request bodies are excluded.
- Manual, frontend, backend, and `[BUG]` signals preserve tenant isolation in
  storage and grouping. Provider delivery receipts contain no incident
  payload.
- Overlapping cron executions are serialized with a PostgreSQL advisory lock.
  Successful fingerprints and CloudWatch transition timestamps suppress
  duplicate sends.
- Audit-storage failure returns 503 for explicit reports. Backend automatic
  capture remains non-blocking; its PII-free application log and the
  independent ALB alarm remain available if the process or database fails.

## 6. Residual Risk

- Database-backed throttling can permit a small concurrent overshoot because
  it intentionally avoids serializing every report request.
- The bounded in-process audit queue can lose an automatic sample if an API
  process exits abruptly. The synchronous PII-free log and independent
  CloudWatch alarm are the compensating controls.

No release-scoped Critical or High finding remains.
