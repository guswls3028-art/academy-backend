# V1.11.5 Release Notes

**Status:** Production-deployed / GO

**Release date:** 2026-07-26 KST

**Scope:** Privacy-safe tenant-attributed user-incident SMS to the single
controlled operator number, with bounded retries and provider delivery proof

## 1. Decision

GO. When production users encounter a monitored server error, browser error,
or explicit problem report, the operator now receives one compact SMS at the
sole controlled number `01031217466`. The message identifies the affected
tenant by platform-issued tenant code and internal ID and gives a normalized,
safe reason so the operator can contact the academy proactively.

Customer-facing product messaging remains Alimtalk-only. This SMS path is the
explicit operator-incident exception and cannot select an arbitrary recipient.

## 2. Delivered Behavior

- One command run aggregates new incidents into one SMS rather than sending one
  message per tenant.
- The message includes a bounded tenant reference such as
  `tenant-code#12:서버500(1)` and only normalized reasons:
  `서버500`, `서버5xx`, `화면오류`, `직접신고`, or `버그제보`.
- Owner-editable tenant names, routes, exceptions, descriptions, user text,
  student/person identifiers, and phone numbers are excluded from the SMS.
- Invalid or phone-like tenant codes fall back to the internal reference
  `T{id}`.
- The SMS is fixed to type SMS, the exact controlled recipient, and a
  90-byte UTF-8 budget. Tenant overflow is represented as `+N곳`.
- Successful sends store tenant/display/omission counts and a body SHA-256
  receipt without persisting the SMS body.
- External infrastructure alarms remain generic when a tenant cannot be
  attributed safely.

## 3. Delivery Safety and Operations

- A send-attempt receipt is created before provider registration. The provider
  group ID is persisted immediately after registration and then reconciled.
- Registered, successful, held, or ambiguous attempts are not automatically
  resent. Only definitive registration or delivery failures are eligible for a
  later retry.
- Unresolved provider groups are reconciled for the two-day incident retention
  window, ten at a time, with checked attempts rotated to avoid starvation.
- Delivery is serialized with the existing advisory lock, bounded by a
  five-minute cooldown and twelve provider attempts per hour.
- The incident scan uses the complete two-day retention window so an older
  definitive failure cannot be skipped by a later successful receipt.
- The operator test path uses the configured owner tenant's platform code and
  internal ID and confirms Solapi's final delivery counters.

## 6. Residual Risk

- The operator SMS contains the minimum tenant reference needed for proactive
  contact. It deliberately omits raw user-provided detail, so deeper diagnosis
  still uses the protected `/dev` console and server logs.
- A provider attempt that becomes ambiguous without a group ID is held for
  manual review instead of being retried automatically. This favors avoiding a
  duplicate SMS over automatic recovery.
