# V1.11.25 Release Notes

**Status:** Production-deployed / GO for the affected admin route

**Release date:** 2026-07-28 KST

**Scope:** tchul clinic-screen deploy-race recovery, bounded lazy-route
retries, regression coverage, and production verification

## 1. Decision

GO for the affected tchul administrator route. A stale application shell could
reach a newly deployed React lazy module before edge propagation had settled.
The resulting `default` module-shape `TypeError` was treated as a generic
screen error, so the existing bounded chunk-recovery sequence did not run.

The error boundary now recognizes that exact failure only when React lazy
context is present. It uses the existing cache-busted, cooldown-controlled
recovery path while leaving ordinary component `TypeError` failures visible.

## 2. Incident Evidence and Repair

- Production `OpsAuditLog` incident `103` recorded
  `user_incident.frontend_exception` for tenant `tchul` on
  `/admin/tools/clinic` at `2026-07-27T12:22:13Z`.
- The incident was six seconds after the preceding Cloudflare deployment
  completed, matching the stale-shell/new-chunk propagation window.
- The reported error class was `TypeError`; the existing `lazyWithRetry`
  contract documents React's
  `Cannot read properties of undefined (reading 'default')` failure shape.
- `isChunkLoadError` is now a pure, directly tested classifier shared by the
  error boundary.
- Module-shape errors require React lazy context. A normal
  `Cannot read properties of undefined (reading 'map')` component failure is
  explicitly kept outside automatic chunk recovery.
- Existing two-minute retry windows, ten-second cooldowns, six-retry limits,
  cache-busted reloads, persistent-error reporting, and manual reload behavior
  are unchanged.

## 3. Compatibility and Boundaries

- Frontend route contracts, API calls, tenant resolution, authentication, and

- No backend runtime code, infrastructure, dependency, database schema, or
  migration changed.
- No production record was created or modified during the final route check.
- The repair applies to any lazy route exhibiting the same deploy-time module
  shape failure, without suppressing unrelated application errors.
