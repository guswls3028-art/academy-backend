# V1.12.7 Release Notes

**Status:** Production-deployed / GO for code, rollout held OFF

**Release date:** 2026-07-29 KST

**Scope:** Privacy-safe role-based product usage signals, tenant-isolated
operations reporting, guarded rollout controls, and evidence-based database
availability and tenant data-plane decision gates

## 1. Decision

GO for the analytics foundation. The backend migration and APIs and the
frontend instrumentation and operator UI are deployed in production. Collection
remains disabled for every tenant, so this release does not begin behavioral
data collection or change any menu, CTA, wording, or navigation priority.

The rollout remains a separate operation. It requires a dedicated analytics
HMAC secret, an explicitly selected pilot tenant, seven days of quality and
capacity evidence, then a representative two-to-three-tenant pilot. UI priority
changes remain prohibited until a 28-day baseline meets the sample rules.

Application multi-DB routing is intentionally not introduced. The current
single `default` database and tenant-column isolation remain canonical. This
release adds sampled, SQL-text-free tenant DB usage evidence so Multi-AZ, read
replica, and selective tenant data-plane decisions can be made from measured
cost and stability signals instead of product page visits.

## 3. Privacy, Tenant, and Failure Contract

- Resolve tenant, active membership, role, and audience group on the server;
  client-supplied user, role, tenant, or actor fields are rejected.
- Store an HMAC-SHA256 actor hash derived from the dedicated secret and
  `tenant_id:user_id`; do not store the raw user primary key, username, name,
  phone, email, query string, entity ID, or free text.
- Fail closed for missing tenant, ambiguous membership, disabled tenant flag,
  or missing HMAC secret. Analytics storage failure remains fail-open to the
  product action and cannot make attendance, submission, or clinic work fail.
- Exclude synthetic and impersonated activity from default product decisions.
- Restrict cross-tenant reporting to the platform operator permission and audit
  access without logging result data.
- Suppress a single-tenant result cell with fewer than five distinct actors and
  distinguish insufficient sample size from observed low use.
- Retain raw events for 30 days and anonymous daily aggregates for 400 days.
  Retention execution remains an explicit, dry-run-reviewed operation.
- Add only new product-analytics tables and indexes in
  `core.0051_product_usage_analytics`; no user-authored or existing domain data
  is rewritten or removed.

## 4. Database Availability and Tenant Split Decision

This release separates three different problems:

- Multi-AZ addresses an RDS instance or Availability Zone outage; it does not
  add read capacity or isolate a noisy tenant.
- A read replica addresses eligible lag-tolerant reads; it does not isolate
  writes, authorization, payment, attendance, submission, or state machines.
- A dedicated tenant data plane addresses contractual isolation, independent
  recovery, or proven noisy-neighbor impact; it does not remove the shared
  control-plane dependency.

No `DATABASE_ROUTERS`, read replica, tenant schema/database, dual-write,
Multi-AZ setting change, or domain-table move is included.

The next decisions use the following gates:

- Review Multi-AZ when approved DB RTO is at most ten minutes, two independent
  production tenants make one DB outage a multi-customer incident, a
  time-critical workflow's outage cost exceeds the incremental cost, or a
  comparable DB/AZ incident occurs. Execute only after Academy-tagged cost,
  budget-with-20%-headroom, snapshot restore, application, health, failover,
  rollback, and ownership gates all pass.
- Review a read replica only after 28 days show at least 70% read DB time,
  query/index/N+1 fixes are exhausted, writer pressure threatens user SLOs,
  candidate reads tolerate lag, and replica cost beats writer scaling.
- Review a dedicated data plane immediately for contractual, legal, residency,
  tenant-specific backup/RPO/RTO, or independent stop/recovery requirements.
  For performance alone, require two consecutive 28-day windows where one
  tenant causes at least 30% of DB time or writes, other tenants experience a
  repeated SLO/connection/writer impact, and the dedicated operating cost is
  contract-funded.
- If one tenant exceeds 25% of storage and is forecast to exhaust shared
  headroom within 90 days, begin the same review. Broad shared growth calls for
  writer scaling, partitioning, or retention changes before tenant splitting.
- If analytics itself projects beyond 20% of current DB free space at 90 days
  or adds at least 10% of writer DB time or writes, stop rollout and reduce or
  separate analytics storage. Do not use that signal to shard product domains.

The long-term target, if a gate is met, is shared control plane plus shared
data plane for most tenants and a dedicated data plane only for qualifying
tenants.

  correctly has no real usage baseline.

  runs them serially with retries. It reached its two-hour workflow limit in
  existing OCR, messaging, document-processing, and destructive-edge
  scenarios; it did not report an analytics contract failure. The canonical
  production workflow's login, tenant, round-trip, and real-use blocking gates
  all passed.
- No feature should be promoted, hidden, or moved from this empty baseline.
  First product-priority decisions require a successful pilot and 28 days of
  sample-qualified evidence.
- DB structure reviews recur every 28 days and remain independent approvals.
  This release supplies evidence and decision criteria, not authorization for
  infrastructure mutation or tenant data movement.
