# V1.12.16 Release Notes

**Status:** Production-deployed / GO

**Release date:** 2026-08-01 KST

**Scope:** Tenant-wide attendance roster ordering, account-and-PC persisted sort
preference, full-list server ordering, and production continuity verification

## 1. Decision

GO. Every tenant now opens an attendance roster in Korean name ascending order
when that account and browser has no saved preference. A teacher's selected sort
is saved per signed-in account on the current PC and restored on later visits.
The API applies the requested ordering before pagination, so the result is
correct across the entire roster instead of only the visible page. The backend
candidate passed persistent development, isolated preproduction, production
migration, health-gated rollout, exact-digest verification, and manifest
promotion. The frontend candidate passed preview, protected production
approval, all-tenant availability, and authenticated real-use verification.

## 2. Attendance Ordering Contract

- `GET /api/v1/lectures/attendance/` accepts the
  whitelisted `ordering` values `id`, `name`, `status`, `parent_phone`, and
  `phone`, plus their descending forms. Missing or invalid values fail safely
  to `name` ascending.
- Ordering is applied to the tenant-scoped, non-deleted queryset before DRF
  pagination. Stable name and ID tie-breakers keep page boundaries repeatable.
- Attendance status uses the product's semantic state order rather than an
  incidental database or translated-label order.
- The frontend includes ordering in both the API request and query cache key,
  avoiding stale page reuse when the teacher changes the sort.
- The table no longer copies and re-sorts only the current page in the browser.
  This removes redundant client work and keeps large rosters globally correct.

## 3. Persisted User Experience

- First use defaults to Korean name ascending (`이름 ▲`).
- The selected table sort is stored under the signed-in user ID in browser
  `localStorage`, which gives account-and-PC scope without adding tenant data or
  a new backend write path.
- Saved state is initialized lazily and is reused across lectures, sessions,
  reloads, and tenants only for the same signed-in account in that browser.
- Invalid or unavailable stored values are ignored and fall back to name
  ascending. No attendance status, memo, score, or other user-authored data is
  changed by sorting.
