# V1.12.0 Release Notes

**Status:** Production-deployed / CONDITIONAL GO with one controlled
operator-tool residual

**Release date:** 2026-07-28 KST

**Scope:** API outage recovery, isolated pre-production deployment gate,
fail-closed runtime environment handling, and production rollout safety

## 1. Decision

The production runtime is GO. Candidate API images and environments now have
to pass on a disposable EC2 instance with dedicated IAM, a candidate-only SSM
parameter, and the `academy_api_preprod` database before production database,
API, worker, Batch, EventBridge, or ALB mutation can begin.

The independent read-only deployment verifier remains CONDITIONAL GO only
because the local Wrangler shell cannot list R2 buckets. Public frontend/API
health, the signed CDN playback chain, AWS runtime state, and the 30-check
production canary all passed.

## 2. Incident and root cause

- Production requests returned HTTP 500 after `/academy/api/env` received
  `DJANGO_SETTINGS_MODULE=apps.api.config.settings.worker`.
- The API URL configuration was therefore invalid for every request even
  though Docker and container health appeared normal.
- The live parameter was atomically restored to
  `apps.api.config.settings.prod`; public health and ALB target health
  recovered.
- The unsafe fallback that could synthesize API configuration from worker
  configuration was removed.

## 3. Deployment safety architecture

- CI now runs `verify-api-preprod` after immutable image construction and
  before production migrations or any of the API, Messaging, AI, Tools, and
  Video deploy jobs.
- Manual deployment prepares API/worker candidates in memory, publishes only
  `/academy/api/preprod/env`, runs the isolated gate, and promotes live SSM
  values only after PASS.
- The preprod parameter is an Advanced SecureString so the current environment
  larger than 4 KB is preserved without truncation or write failure.
- The canary uses the dedicated `academy-api-preprod-canary-role` and instance
  profile. It can pull only the API image and read only the candidate
  parameter; it is never attached to the production ASG or ALB.
- The GitHub deployment role can terminate only instances carrying all three
  canary tags. IAM simulation returned `allowed` for the canary tag set and
  `implicitDeny` for the real production API instance.
- Canary user data creates or reuses only `academy_api_preprod`, applies
  candidate migrations there, validates prod settings and the database
  boundary, then checks `/healthz`, `/health`, exact image digest, and the
  signed HLS master/variant/segment chain.
- Canary instances have both a 30-minute instance-initiated termination
  backstop and `finally` cleanup. Cleanup failure fails the gate.
- SSM remote proof execution is normalized across Windows and Linux by
  removing CR characters, Base64-encoding the script, and explicitly invoking
  Bash.

## 4. Fail-closed production behavior

- API and worker SSM values enforce distinct settings modules and reject
  missing or cross-role source data.
- API user data requires SSM retrieval and exact prod settings, writes the env
  file atomically, and fails when real health does not recover.
- Formal deployment no longer restarts a production API container in place.
  The API env parameter version participates in the Launch Template deployment
  identity and uses an ASG rolling refresh.
- Live API/worker parameter promotion has compensation rollback. Promotion or
  rollback failure is surfaced instead of hidden.
- Manual worker ASGs, Batch definitions, EventBridge, ALB, and API convergence
  all occur after the common canary and live-env promotion gate.
- Re-running the converged deployment kept API LT 157, Messaging LT 56, AI LT
  56, and Tools LT 43 unchanged and started no new instance refresh.

## 7. Six-lens audit closure

- Reliability: common preprod dependency precedes migrations and every
  production deploy job; manual runtime mutation order is equivalently gated.
- Security: canary role, profile, parameter access, PassRole, SendCommand, and
  termination permissions are resource- and tag-bounded.
- Data safety: candidate migrations use a separate database; production
  migrations occur only after preprod PASS.
- Failure handling: parameter promotion and API refresh rollback failures are
  visible; canary cleanup is mandatory.
- Runtime correctness: API and worker settings modules cannot cross-contaminate
  and both real health endpoints are required.
- Operations: shared mutation locking, immutable digest checks, idempotence,
  production canary, netprobe, and atomic evidence were verified.

Critical findings: 0. Reachable high findings: 0.
