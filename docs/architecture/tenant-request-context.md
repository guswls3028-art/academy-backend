# 요청의 학원 선택과 실패 경계

현재 구현은 `apps/core/tenant/resolver.py`, `apps/core/middleware/tenant.py`,
`apps/api/common/auth_jwt.py`가 소유한다. 학원 선택은 브랜딩·공개 자료와 모든
인증된 업무의 조회 범위를 정한다. 학원 선택만으로 객체 접근 권한을 부여하지
않으며, 인증 토큰의 학원·활성 멤버십·각 도메인의 객체 권한 검사가 뒤따른다.

## 정상 요청

- 중앙 API와 설정된 개발 호스트는 `X-Tenant-Code`로 활성 학원을 선택한다.
  코드는 공백을 정리하고 대소문자를 구분하지 않는다.
- 일반 학원 호스트는 `TenantDomain`을 사용한다. 이 호스트의 헤더는 다른
  학원으로 바꾸는 수단이 아니다. 도메인과 학원이 모두 활성 상태여야 한다.
- 헤더가 없는 `/api/v1/landing-public/` 요청은 기존 `?tenant=<code>` 계약을
  유지한다. PDF 등 브라우저 기본 문서 요청은 사용자 정의 헤더를 넣을 수
  없기 때문이다. 다른 API의 query parameter는 학원을 선택할 수 없다.
- 헤더·공개 query로 선택되지 않은 요청은 기존 호스트 매핑을 사용한다.
  매핑되지 않은 ALB 호스트의 명시적 헤더 선택도 같은 유효성 검사를 적용한다.
- 로그인·토큰 갱신, health, 내부 경로와 결제 webhook의 기존 middleware
  bypass는 유지한다. 로그인은 `auth_jwt.py`에서 별도로 학원을 결정한다.

## 명시적 선택 실패

지원되는 선택 위치에 값이 **있지만** 빈 값·공백·없는 코드·비활성 학원이면
즉시 `404 / tenant_invalid`로 종료한다. 대소문자 무시 조회에 활성 학원이 둘
이상 일치해도 임의의 첫 행을 선택하지 않는다. 로그인도 같은 코드 조회를
사용하므로 모호한 선택에서는 토큰을 발급하지 않는다. 다른 query나 호스트 학원으로
대체하지 않으며, view를 실행하거나 성공 응답의 학원 헤더를 붙이지 않는다.
존재하지 않는 학원과 비활성 학원의 차이를 이 응답으로 노출하지 않는다.
정상 헤더가 있으면 그 선택이 공개 query보다 우선한다.

값을 아예 보내지 않은 요청과 빈 값을 명시한 요청은 다르다. 전자는 기존
호스트 선택을 허용하지만, 후자는 잘못된 선택이므로 실패한다. 클라이언트는
올바른 학원 코드로 다시 요청해야 하며 기본 학원으로 자동 재시도하면 안 된다.
정상·실패·bypass 모두 요청 종료 후 contextvars의 학원 값을 비운다.
대소문자 중복은 정확한 학원 코드/운영 설정을 정리한 후 다시 시도한다. 이 수정은
기존 코드를 자동 변경하거나 학원을 비활성화하지 않는다.

이 변경은 데이터나 도메인 매핑을 수정하지 않고, 올바른 기존 홈페이지·앱·공개
문서 URL을 유지한다. 잘못된 선택이 우연히 다른 학원에서 성공하던 동작만
중단한다. 단순한 학원 식별 실패를 실제 운영 정보 유출 증거로 간주하지 않는다.

## 검증

`apps.core.tests.test_tenant_explicit_selection`은 활성 호스트와 다른 학원을
동시에 둔 상태에서 잘못된/빈 헤더·공개 query·ALB 요청의 거절, 정상 선택,
호스트 우선권, 공개 문서 링크, 비공개 API의 query 무시, context 정리,
실제 Program API의 선택된 브랜딩 응답을 검사한다. 대소문자 중복 시 헤더·공개
문서와 로그인 거부, 활성 중복이 해소된 뒤 로그인 복구도 검증한다.

`test_tenant_middleware_bypass`, `test_jwt_tenant_claim`,
`test_me_parent_student_tenant_isolation`은 로그인·토큰과 학생/학부모 계정의
연결 경계를 함께 검증한다. 운영 반영에는 필수 CI와 격리 개발/사전 운영 및
공식 배포 게이트를 적용한다. 전체 인증 도메인의 완료 상태는
[도메인 점검 지도](../refactor/domain-quality-map.md)가 별도로 추적한다.
