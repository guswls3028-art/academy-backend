# Academy 실행 계획

- **상태:** active · Academy 전체 작업의 실행 순서와 인계 기준
- **갱신일:** 2026-10-10 KST · 전체 도메인 1차 구조 대조·수정·배포 증거와 기능 발견성 운영 반영. 학생 일괄 처리 후속·보안 수정 운영 반영 및 화면/서버 묶음 검증 완료. 정확한 후보와 미검증 범위는 [전체 점검 지도](refactor/domain-quality-map.md)에 기록
- **갱신 조건:** 우선순위·범위·완료 판정이 바뀔 때, 그리고 각 작업을 마칠 때

이 문서는 Academy에서 **다음에 무엇을 왜 할지** 정하는 단일 진입점이다. 작업별
설계·재현·검증 기록은 소유 문서와 PR/CI에 둔다. 현재 제품 동작은 코드·실행
워크플로·런타임 확인과 [현재 정책·운영 문서](README.md)가 소유하며, 이 계획의
날짜가 붙은 판단만으로 배포 상태나 결함의 현재성을 주장하지 않는다.

## 1. 목표와 판단 기준

학원의 서로 다른 운영을 하나의 의미 체계로 표현하고, 각 역할의 사용자가 화면에서
업무를 끝내고 저장 결과를 다시 확인할 수 있게 한다. 원천 사실·사용자 판단·자동
제안을 구분하고, 테넌트·권한·수동 작성 자료를 보호한다. 설계 원칙은 워크스페이스
`docs/PRODUCT_PHILOSOPHY.md`, 시스템 경계는 `C:\academy\ARCHITECTURE.md`를 따른다.

작업 순서는 다음 질문으로 결정한다.

1. 실제 사용자나 데이터가 지금 피해를 보는가? 테넌트 누출, 데이터 손실, 인증·핵심
   업무 실패, 릴리스 안전 게이트 실패는 먼저 처리한다.
2. 정상 사용자가 진입 → 실행 → 저장 → 재열람 → 다른 역할의 소비까지 마칠 수 있는가?
3. 실패·대기·빈 결과가 구분되고 입력 보존·재시도·복구가 가능한가?
4. 구조 변경이 그 결과를 더 안전하고 단순하게 만드는가? 측정 가능한 중복·경계
   문제나 실제 변경 비용이 없으면 코드 이동 자체를 목표로 삼지 않는다.
5. 새 기능은 기존 사실·정책·상태·템플릿의 조합으로 표현 가능한가? 새 표현 단위가
   필요하면 소유권·호환·검증을 먼저 결정한다.

## 5. 작업 카드와 완료 판정

PLAN-00 이후 §3의 후보를 실제 사용자 결과가 있는 작업으로 좁혀 §2에 **한 줄씩**
올린다. 한 줄에는 사용자 결과, 우선순위와 이유, 담당 저장소·소유 세션, 선행 작업
ID·현재 단계·정확한 다음 행동을 적는다. 막힌 경우에는 결정권자, 해결할 정확한
질문과 영향 범위, 재개에 필요한 증거와 유효 HOLD의 소유 기록을 연결한다.
소유 문서·PR·CI도 링크한다. 한 작업이 길어지면 로그를 이 파일에 붙이지 않고
해당 소유 문서에 기록한다. 완료·보류·폐기한 줄에는 날짜와 증거 또는 이유를 남긴다.

제품 변경의 완료는 화면 진입 → 실제 역할의 동작 → 서버 저장 → 새로고침 → 소비
화면을 포함한다. 관련 실패·재시도·중복 실행, 테넌트/권한 경계, PC/390px,
집중 검사와 필수 CI, 현재 기능 문서, 필요한 격리 실사용·정리 0과 운영 readback을
변경 범위에 맞춰 확인한다. 증거가 부족하면 `완료` 대신 `미검증`으로 남긴다.
상세 게이트는 [변경 위험·릴리스 증거](operations/change-risk-and-release-bundle.md),
각 저장소 `AGENTS.md`와 실행 워크플로가 소유한다.

## 6. 갱신 규칙

- 새 요청은 먼저 §1의 결과와 §2의 현재 작업 중 어디에 속하는지 판정한다.
  우선순위가 바뀌면 밀린 작업의 상태와 이유를 함께 갱신한다.
- 한 작업을 시작할 때 날짜·소유 세션·출발 SHA와 성공 조건을 기록한다. 끝날 때
  PR/CI/릴리스·사용자 결과를 연결하고 다음 한 행동을 남긴다.
- 계획의 지난 시점 판단은 삭제해 현재 사실처럼 다시 쓰지 않는다. 짧게 종료
  이유를 적고 상세 이력은 소유 문서·PR/보고서에 둔다.
- 테넌트 자료, 개인 정보, 비밀, 장문의 운영 로그는 이 파일에 넣지 않는다.
- 이 파일은 승인, HOLD 해제, 배포 게이트 통과를 대신하지 않는다. 현재 효력이 있는
  조건은 해당 운영 문서와 플랫폼 readback에서 확인한다.
- 서로 다른 작업의 동시 진행과 릴리스 소유권은
  [동시 세션 절차](operations/concurrent-codex-sessions.md)가 정한다.
